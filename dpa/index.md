# Business Customer Data Processing Addendum (WholeTake Cloud)

> This document is not legal advice. It has not been reviewed by a lawyer; it was written from public law, Paddle's requirements and the published practice of similar products, and it describes how the service actually works. Retention periods, allowances and prices are those shown on the pricing page.

## 1. Parties and scope

- **Scope**: this addendum applies only when a customer uses WholeTake Cloud as an organisation (for example a company or school) and processes other people's personal data in it: the customer is the controller and the operator is the processor. When someone uses WholeTake for personal or household purposes, the operator is the controller, the [privacy policy](https://wholetake.marlubie.com/privacy/) applies and this addendum does not.
- **Processor**: the operator of WholeTake Cloud, operating as Marlubie (identity and postal address under "Operator" in the [privacy policy](https://wholetake.marlubie.com/privacy/)). Once a Taiwanese single-member limited company is set up, operation transfers to it under the "Changes to these terms and to the operator" section of the terms of service, and this addendum transfers with it. Contact: support@marlubie.com.
- **Controller**: the customer who uses WholeTake Cloud as an organisation and processes other people's personal data in it.
- **Formation**: this addendum applies to business customers who accept the terms of service and is part of the whole agreement listed in the terms' "General" section; email us for a signed copy.

## 2. Subject matter, duration, nature and purpose

- **Subject matter**: data the customer uploads or creates when using WholeTake Cloud — the cloud copy (knowledge records, concept library, topic pages), cloud-task results and page snapshots, knowledge packages published to the community, and AI request content (including the knowledge-graph tag names and aliases sent for auto-tags).
- **Duration**: from when the customer turns WholeTake Cloud on until account deletion or deletion at the end of retention (see [Data retention](https://wholetake.marlubie.com/privacy/retention/)).
- **Nature**: storage; syncing to the customer's devices and web app; sending the task content the customer triggers to upstream models and returning the result; fetching public web pages per the customer's settings; publishing publicly when the customer chooses to.
- **Purpose**: only to provide the service the customer requests; no model training on customer data, no sale, no advertising.
- **Instructions**: the processor processes personal data only on the controller's documented instructions; the controller's settings and use of the service are those instructions. If the law requires other processing, the processor informs the controller first unless the law forbids it.

## 3. Categories of personal data and data subjects

- **Categories**: account data (email, device names); IP addresses and browser strings recorded for sign-in sessions and security-event audits; a keyed hash of the email address used to prevent repeated trials; any personal data the customer's web content, summaries, notes and Q&A may contain (the customer decides what to upload; the operator does not screen content); usage records (no content) and cloud-task records (the task's URL, title and a content hash, no page text).
- **Data subjects**: the customer; third parties appearing in the pages and notes the customer processes.
- **Special categories**: the service is not designed for special categories of personal data, and the controller should not upload them; if it does, they are protected by the same measures in section 5.

## 4. Subprocessors

The operator's subprocessors are listed under [Subprocessors](https://wholetake.marlubie.com/privacy/subprocessors/). By this addendum the controller gives the processor general authorisation to engage the subprocessors on that list. When a subprocessor is added or replaced, the processor updates the list and notifies the controller at least 30 days in advance; if one must be replaced urgently (for example, because it stops its service or after a security incident), the processor notifies the controller as soon as it can and explains why. If the controller objects on reasonable grounds, it may end the service and the processor refunds the unused part of the current period pro rata. The processor imposes data protection obligations on each subprocessor equivalent to those in this addendum.

## 5. Security measures (engineering facts)

- **In transit**: the Extension and the web app always use HTTPS; Extension requests carry no cookies and identify only with account tokens; the server host is fixed at build time and cannot be changed by the user; cross-host redirects are never followed.
- **At rest**: the database and file storage are encrypted by the service providers; the cloud copy is not end-to-end encrypted at launch (a recorded decision).
- **Access control**: every database table has row-level security enabled with no direct-access policies and public roles revoked, so only the server code can reach it; the admin console requires sign-in plus two-step verification, and moderation actions are audit-logged.
- **Minimisation**: server logs record only the route, status code, error code, IDs, size and duration — never content, URLs, titles, prompts, output, tokens or email; the usage ledger holds no content; no third-party analytics; AI request content and output are not stored.
- **Secrets**: server and third-party keys are kept in the platform's secret store and rotated per the rotation procedure; provider keys added in the admin console are encrypted with a key-encryption key before being stored in the database.
- **Backup and restore**: every day the operator stores copies of the database (a snapshot) and of file storage in Cloudflare R2's Western Europe region (a different region from the database and file storage), encrypted with a public key whose private key is kept offline, so the server holds only the public key and cannot open the backups (on a day when encryption fails or the key has not been confirmed, that day's backup is written unencrypted and the operator is alerted); each database snapshot is kept for 30 days (if database exports keep failing, the latest complete snapshot is kept until the next complete one exists), and a copy of an attachment whose original was deleted is kept for another 30 days from the day the backup job finds the deletion (how this counts when a large deletion trips the guard against mass deletion is in section 8); if the previous backup did not complete, the server alerts the operator. A restore checks every file's hash and row counts before writing anything. When an account is deleted, a deletion record is also kept (a one-way SHA-256 hash of the account's random ID and the deletion date, in the same off-site backup storage, never modified after it is written); when only Send to cloud for processing records are deleted and the account is kept, a record of the same form is kept (the same one-way hash, plus the time and kind of deletion). Deletion records and their index are not encrypted; the server can read them to clean them up. When restoring from the operator's off-site backups or the database provider's backups, account deletion is paused first and, before the service is reopened, deleted accounts are deleted again according to the deletion records (the trial identifier, settlement of auto-renewal consent records and audit records follow the account-deletion rules), and deletions of only Send to cloud for processing records are redone; where this cannot be done because the deletion records are lost as well (for example, if the off-site backup storage and the database fail together) or writing a record failed and could not be retried before the database was lost, the operator records it under section 6 and assesses whether to notify. Deletion records are kept for 32 days and then deleted by a daily job. A restore drill is run once before going live and every quarter after that; the drill records are listed in section 9. In addition, the database provider (Supabase, paid plan) makes daily backups, kept as stated in the data retention policy. The production backup key was confirmed before the first production deployment, so no production backup is written unencrypted because of an unconfirmed key.
- **Server-side page fetching**: internal-network, local and reserved addresses are refused; robots.txt and noai directives are obeyed.

The engineering facts in this section are the security annex. The processor reviews them at least once a year and updates this section after significant changes, and ensures that people authorised to process personal data are bound by confidentiality.

## 6. Personal data breaches

The processor notifies the controller without undue delay, and at the latest within 48 hours of confirming it, of a personal data breach affecting the controller's data, with the information then available (nature, accounts and data categories affected, likely consequences, measures taken or proposed), followed by updates. Server logs carry no content, so assessment relies on IDs and a timeline.

## 7. Assisting the controller with data subject requests

The processor helps the controller respond to data subject requests and meet its obligations under GDPR Articles 32 to 36 through the self-service tools (full backup download, deleting items one by one in the web app, deleting the account) and the manual process described in [Data subject requests](https://wholetake.marlubie.com/privacy/dsr/), at no charge; for help beyond a reasonable scope, the processor may charge a reasonable fee agreed in advance.

## 8. Deletion and return

- **Return**: the customer can download a full backup from the account page at any time (machine-readable, importable into the Extension).
- **Deletion**: when the account is deleted, the database data the account owns is deleted with it, and file storage is deleted by a scheduled job that retries until done; an automated test checks every table for residue after account deletion — **except the items kept under the [data retention policy](https://wholetake.marlubie.com/privacy/retention/)**: security-event audit records (including the account-deletion record; the random IDs of the deleted account and devices, and the IP address and browser string at the time), moderation audit records, the trial identifier (a keyed hash of the email address), and the content fingerprints recorded when a knowledge-package edition is taken down or removed for legal reasons, or when a public knowledge graph / topic page is removed for legal reasons (a SHA-256 hash plus the ID of the item acted on, with no field linking it to an account). None of them contain page content, and a daily job deletes each one at the end of its period in the data retention policy. Reports are kept after the reporter deletes their account: the reporter field is cleared, and the report's reason category and description stay until the end of the period, when a daily job deletes them. Paddle payment event records without an account ID are the operator's own billing records, which the operator keeps as a controller in its own right (not on the customer's behalf) for the period in the data retention policy; auto-renewal consent records (when the user agreed, the plan, the billing cycle and the version of the disclosure text, linked to the account only by its random ID) are likewise kept by the operator as a controller in its own right, to show that automatic renewal was agreed to before payment, and a daily job deletes them at the end of the period in the data retention policy. The residue test looks for the account's ID; in the database, only two places deliberately keep the account's random ID: the account-deletion audit record (which records the deleted account's random ID) and the auto-renewal consent records (until their period ends). Outside the database, the operator's off-site backup storage holds two more: deletion records, which keep only a one-way hash of the account's random ID and the deletion date (kept for 32 days and used, when restoring from a backup, to delete the account again before the service is reopened; see section 5 for when this cannot be done), and attachment-copy paths, which contain the account's random ID and disappear when the backups rotate out as described below. An account with a subscription still being billed, or with community content still published, has to cancel or unpublish it first. At the end of a plan, data is deleted per the retention period. Copies in backups disappear when the backups rotate out: the database provider's daily backups after 7 days; in the operator's off-site backups, each database snapshot is kept for 30 days (if database exports keep failing, the latest complete snapshot is kept until the next complete one exists), and a copy of an attachment whose original was deleted is kept for another 30 days from the day the backup job finds the deletion; when a large deletion trips the guard against mass deletion (for example, deleting an account with many attachments), the period starts only after the operator confirms the deletion was normal and lets it through, and while file storage is being recovered and attachment backups are paused, no copies are deleted.
- **Confirmation of deletion**: on request, the processor confirms in writing that deletion is complete and lists the items still kept under the data retention policy, with their periods.

## 9. Audits

The processor makes available the information needed to show compliance (section 5 of this addendum, the subprocessor list, the restore drill records and other documents it can provide). Restore drills were run twice in the test environment before going live (2026-11-05 and 2026-11-07; no customer data): each time, one daily backup from the operator's off-site backups was decrypted, every file's hash and row counts were checked, and it was restored to a new, empty database, where row counts were compared table by table and reconciled; the 2026-11-07 drill also exercised the deletion handling for a restore described in section 5: account deletion was paused first, deletions were redone in the restored database from the deletion records (the account in one account deletion record was deleted again; one record of deleting only Send to cloud for processing records was also processed as specified, though that test account had no such records to delete), and the pause was lifted only after the checks. Each quarterly drill after that is added to these records. The controller may request an audit once a year, carried out mainly through written questions and documents, and additionally where there is a specific reason to suspect a breach or a supervisory authority requires it. The controller bears the cost unless the audit finds a material breach.
