# Privacy Policy

**"WholeTake" Chrome Extension**

Last updated: 2026-09-26

---

## Overview

"WholeTake" (formerly "AI Web Summary & Translate"; the "Extension") is maintained by an independent developer. It helps you summarize and translate web pages using a large language model (LLM) endpoint that **you configure yourself**.

We take your privacy seriously. This policy explains what data the Extension processes, how, and what your rights are.

In one precise line: **This version ships exactly two AI paths — your own key (BYOK) straight to the endpoint you choose, or Chrome built-in AI running on your device; neither goes through a developer server, and there is no telemetry. On the BYOK path your content goes only to the AI endpoint you configure; with built-in AI, inference runs on your device; results are kept locally by default.** Exactly what each feature sends, whether it is automatic, and how many model calls it makes are laid out in the **data-flow matrix (DATA_FLOW.md)**.

---

## No developer collection, no telemetry

This version ships exactly two AI paths: **your own key (BYOK)** straight to the endpoint you choose, or **Chrome built-in AI** running on your device. On both of them the developer collects **no user data on any server** (note, however, that **your page content is sent to the AI endpoint YOU choose** — that is the nature of BYOK, which is different from "sends no data anywhere"). The Extension:

- Contains no trackers or analytics (Google Analytics, Mixpanel, etc.)
- Shows no ads
- Sends nothing to the developer (this version has no channel that leads to us)
- Both of this version's paths — your own key (BYOK) and Chrome built-in AI — run with no developer-operated server and no intermediary (summary and translation content goes only to the AI endpoint you configure; with Chrome built-in AI it stays fully on-device. The single exception is the "Optional public knowledge-base lookup (Wikidata)" below — its main switch is **off by default** (offered unticked both in the setup wizard and in Settings); once you turn it on, it sends one concept name when you click "Find public mapping", and also the new tag names of each summary (at most 6, names only, not re-sent for 30 days) when its tags are generated (the sub-option "Automatically look up public mappings for new tags" is ticked by default, takes effect only while the main switch is on, and can be unticked on its own); never any page content)

## Data processed locally on your device

### 1. Settings

Everything you enter on the Settings page is stored only in your Chrome browser's storage:

- AI provider choice (Chrome built-in AI, AWS Bedrock, or OpenAI-compatible) — **Chrome built-in AI (Gemini Nano) is key-free and runs entirely on-device**: choosing it requires no API key, and model inference for summaries/translations makes no external requests (see "Chrome built-in AI mode" below for details)
- Bedrock API Key (if using Bedrock; v1.14 uses a Bearer API key instead of Access/Secret keys)
- AWS region, Bedrock model ID
- For the three "independent model" slots (summary / translation / knowledge base), an optional Bedrock API Key and AWS region of their own (since v1.46; leave blank to reuse the main one — stored under exactly the same storage mode as the main key)
- OpenAI-compatible endpoint URL, API key, model name
- Summary / translation prompt templates (including per-length custom versions)
- Translation color, translation font and size, bilingual display preference, translation scope
- Whether to include page images, result display mode (dialog / side panel)

The Extension's own pages also use `window.localStorage` (not `chrome.storage`) for **11 display and
ask-panel preferences only** — numbers, booleans, layout coordinates and your interface language (`kgAskDeep` decides whether a question reads all candidates in batches, i.e. how many model calls it makes — not layout; the candidate cap, batch size and batch limit are ordinary adjustable settings from v1.51 (defaults 48 / 8 / 6; 0 = unlimited, still hard-capped at 60 batches) — larger values mean more calls, billed by your own endpoint as always). They
contain **no page content, no credentials and no personal data**, are never synced and never leave
your device:
`wt-theme` (light/dark/auto theme, used to avoid a first-paint flash), `kgAskPanelW` /
`kgAskFontPx` (knowledge-graph ask panel width and font size), `kgAskBox` (where the answer window was dragged to and how big it is — four numbers), `kgAskDeep` (the ask panel's "deep search" toggle, one boolean), `kgLegendOpen` / `kgLegendBox`
(legend collapsed state, window position and size), `spFontPx` (side panel font size),
`wt-options-advanced` (whether the settings page shows its advanced settings — one boolean),
`wt-uilang` (the interface language you chose and its text direction, again to avoid a
first-paint flash), and `wt-uilang-pack` (an offline copy of **the Extension's own** interface
text file for that language — literally the `_locales/<lang>/messages.json` that ships inside the
Extension, cached so the first frame can already be in the right language; it contains none of
your data).
To clear them: use your browser's "Clear browsing data -> Cookies and other site data", or remove
the Extension.

Keyboard shortcuts are **not** in that list: since v1.39 the Extension has no in-page
shortcut handling of its own, and the three browser-level shortcuts are managed by
Chrome's own **Keyboard shortcuts** page (`chrome://extensions/shortcuts`) and stored
by Chrome, not by the Extension.

**Where your API keys live is your choice:**

Keys have **three** storage modes, chosen under Settings → Key Storage:

- **Default — "this device only"** (`chrome.storage.local`): API keys (the Bedrock API Key — including the per-slot ones of the three independent models — and any OpenAI-compatible keys) **never leave this device** and are not synced through your Google account.
- **"Keep keys only until the browser closes"** (`sessionCreds` in `chrome.storage.session`, added in v1.37): keys are **never written to disk and never synced**, and are cleared automatically when the browser closes — you will need to re-enter them next time. Recommended for shared computers and high-sensitivity environments. Requires "Keep API keys only on this device" to be checked first.
  A note so this is not oversold: this is **not a password vault** — while the browser is open, the Extension's trusted contexts (background service worker, Settings page) still read it in order to call the AI endpoint you configured.
- If you uncheck "Keep API keys only on this device" under Settings → Key Storage, keys are stored in `chrome.storage.sync` and sync across your signed-in Chrome devices (**not additionally encrypted**).
- Other non-sensitive settings (model choice, prompts, etc.) always use `chrome.storage.sync` so they follow you across devices.

In every one of this version's key-storage modes, none of this is ever sent to a developer-operated server or any intermediary (only to the AI endpoint YOU configured, when the Extension calls it). We still recommend:

- Do not store high-privilege API credentials on public/shared computers
- Rotate API keys regularly
- Use least-privilege IAM policies (for Bedrock)

### 2. Page content

When you actively trigger "Summarize" or "Translate", the Extension sends the following to **the AI endpoint you configured yourself** (when you right-click a web link and choose "Summarize link in new tab" / "Translate link in new tab", the Extension first opens that link in a new tab, waits for the page to load, and then does the same thing on that page — what is sent is that new tab's content, exactly as if you had opened it yourself and pressed Summarize):

- The **article body text** of the current tab (the primary extraction path checks actual rendering per paragraph and skips invisible ones; the Readability fallback path removes top-level CSS-hidden and `hidden`/`inert` blocks before parsing — small amounts of text hidden by deeply nested stylesheet rules may still be included, so we do not claim it is strictly identical to "what is visible on screen")
- **The page URL (sanitized) and title** — the URL placed in the summary prompt is **only `origin+pathname`**: before sending, the Extension **strips the query string (including access tokens / signed-URL parameters), the `#fragment`, and any userinfo credentials** (see `sanitizeUrlForModel` in `src/defaults.js`); path segments that look like access tokens (an online document's long ID, the code in a password-reset link) are replaced with "…", and the path is capped at 120 characters. The full original URL is kept **only on your device** (history and cache matching) and is never sent out. The title and URL are placed inside the prompt's **data block**, marked like page content as "data, not instructions"; if your custom prompt does not reference the URL, the URL is not sent.
- (If you enabled "include images" and use a vision-capable model) page images. When summarizing a web page, the Extension sends the page's images **one at a time** to the model you configured to get a short text description (one request per image; up to 12 with an OpenAI-compatible endpoint or AWS Bedrock, 3 with Chrome built-in AI — images beyond that are not sent), places each description right after the paragraph that contains the image, and the final summary request contains text only (the PDF reader still attaches its crops — see "PDF summaries / translations" below). Descriptions end up in two places: (1) a temporary in-memory cache in the Extension's background process (gone when the browser idles that process after about 30 seconds, when the browser closes, or when the Extension restarts), so that pressing "Regenerate" shortly afterwards does not resend the same image — images that failed to be read are not cached and are sent again on regenerate; (2) the first 200 characters of each description are stored as that image paragraph's excerpt together with the summary in your local "Recent results" (same lifetime as the summary; included in export and backup; deleted together with the record). A summary served from earlier results (no regeneration) sends no images at all. When collecting page images, the Extension does not take images inside same-site ad frames and does not request 1×1 / 2×2 tracking beacons on your behalf; other small non-content images (under 32 px wide or tall, or under 10,000 px in area) are still downloaded to read their size but are never sent to the model. Image fetching first goes through the service worker without your cookies (`credentials: 'omit'`); only if the image host blocks that (hotlink protection / WAF) is it re-fetched once from the page context. Fetched images are converted to base64. Image URLs pass a safety check (blocking non-http(s), localhost, private and link-local IPs); this check is based on the literal hostname and **cannot defend against DNS rebinding** (a public domain maliciously resolving to an internal IP) — this is a known, accepted residual risk that cannot be fully fixed in this version's architecture — a pure browser extension that sends content only to the endpoint you configure, with no intermediary server. Security-sensitive users can uncheck "include images" to disable all image fetching entirely.

On both of this version's paths — your own key (BYOK) and Chrome built-in AI — the developer has no access to this data and operates no intermediary server.

**What happens with unencrypted (`http://`) endpoints** (as of v1.44): your content only ever goes
to the endpoint you configured yourself, but sending it in the clear is a risk in its own right, so
the Extension checks twice — once when you save the setting, and again immediately before every
request it sends:

- **`https://`** — always allowed.
- **Local loopback** (`localhost`, `127.0.0.1`, `[::1]`) — allowed: the traffic never leaves your
  computer (the default Ollama / LM Studio setup).
- **An IP address on your own LAN** (e.g. `http://192.168.1.50:11434`) — **refused by default**.
  To use one you must explicitly opt in under "Settings → Model settings → Advanced (risk options)",
  because other devices on the same network can sniff plaintext traffic.
- **A LAN endpoint addressed by hostname** (`http://ollama.local`, `http://nas:11434`) — content
  follows the rule above; but **if that endpoint has an API key, it is refused outright and no
  setting can allow it** — such names carry no authentication, so any device on the same network
  can claim the name and receive your key. Use the machine's LAN IP address instead, or `https://`.
- **An `http://` endpoint on the public internet** — **always refused, with or without a key, and
  there is no setting that turns this off.** (Before v1.44 an internal field allowed this case; it
  has been removed entirely.)

The technical criteria and where they are implemented are in the "endpoint transport policy" table
in SECURITY.md.

**Automatic calls beyond the summary itself** (on by default, all to your same model endpoint, each can be turned off in Settings):

- **Auto tags**: after the summary completes, one extra small call sends the **summary excerpt (up to ~4,000 characters)** plus the title and those of your existing tags that **literally overlap with this page** (tag names and the aliases you have confirmed; tags with zero literal overlap are never sent) to extract 3–6 topic tags. When the main summary is served from cache and that record already has tags, this call is not re-run; an older record missing tags gets a one-time backfill call whose result is saved back (a failed backfill is remembered, so it is not re-billed on every cache hit).
- **Suggested questions**: since v1.35, with your own AI endpoint (BYOK) a full-page summary produces the 3 follow-up questions **in the same single summary call** — on that normal path no separate model call is made and no additional content is sent for them. A separate small call sending the **summary excerpt (up to ~4,000 characters)** happens only when the question section of the summary output fails to parse (one automatic fallback call), with Chrome built-in AI (which deliberately keeps the two-stage flow), or for a **selection summary** (its prompt has no inline question section, so the questions are always a separate call). The questions are saved **on your device** alongside that summary; **when the main summary is served from the local cache, the saved questions are reused directly — no extra model call** (an older record missing questions gets a one-time backfill call whose result is saved back).

Topic pages, mind maps, and knowledge-base Q&A are **manually triggered** (see Section 3 below and DATA_FLOW.md). Exactly what each feature sends, whether it is automatic, and the estimated number of model calls are laid out in the **data-flow matrix (DATA_FLOW.md)**.

**Export diagnostics** (`CORE-1510-F4`): Settings → About (next to "Feedback") can export a diagnostics file to help us debug — the file is only downloaded to your device, **never sent anywhere by itself**; whether to hand it to the developer is your call. By default the file contains: end-of-task snapshots for the last ≤50 tasks (timestamps, cache decision, call count, error code, provider and model name, the endpoint's masked label; field by field in the "Diagnostics ring" item below — including YouTube caption-source codes, PDF reader layout counts and the summary processing trace, all fixed codes and numbers), the most recent translation outcomes (URL and host name reduced to hashes), queue and index state, the running-task snapshot, the wipe generation, the extension version and Chrome major version, the storage-protection status (ok / unsupported / failed / pending — whether extension scripts on web pages can read local storage; see SECURITY.md), and a non-sensitive subset of your settings — **no URL, no page text and no key** (allow-listed writer; any URL-like string is dropped whole, credential-shaped strings become `***`, endpoints appear only as host + short hash — so level 1 carries no full URL, no path and no query string, only each endpoint's origin). Only if you tick "include content" will tasks started afterwards also record the model's raw output, your most recent conversation contexts (including page text), the per-paragraph source and translation of a full-page translation, the full URLs of translation outcomes, and — for the last 5 summaries — the instruction shell that was sent (page text replaced by a hash code), the text of any automatic correction instructions (which may quote table rows and cited paragraphs from the page) and the full final summary — that file lives only in your Downloads folder; share it only with someone you trust; after the export the box unticks itself and the retained content is removed at once.

**YouTube summaries**: on a YouTube video page, the Extension reads the video's caption data from YouTube within that page (the primary path does not use your signed-in credentials; only if it fails, a fallback retries using your existing YouTube session within that page — all reads stay inside the YouTube page and nothing is ever sent to the developer); the caption text is then sent to the AI endpoint you configured (or processed fully on-device by the built-in AI).

**PDF summaries / translations** (v1.49+): when you press Summarize or Translate on a PDF open in Chrome's built-in viewer, the Extension opens its own reader page and **downloads that PDF again from its source URL**: the Extension's background makes this one download, replaces the original tab with the reader page only once the first bytes confirm the URL still returns a PDF, and hands the downloaded file to the reader page (the reader does not ask the site a second time); if it clearly does not return a PDF, the original viewer is kept and a new tab asks you to drop the file in; if the server does not answer within 8 seconds the tab is replaced as usual and the download continues — this step only prevents your copy of the PDF from disappearing, it is not an access control. The reader page downloads the file itself only if the browser shut down the Extension's background before the reader received the file, or when you reload the reader page. Every download uses your existing browser login state (so PDFs behind a login wall work too) and goes to the URL you are already viewing — not to any new third party, and never to the developer; the downloaded file is held only in memory on your device, never written to the Extension's storage. If the server redirects the request to **a different site** this time, the Extension **does not read** the redirected content for your safety and asks you to save the file from the viewer's download button and drop it into the reader instead. The file is parsed on your device by a bundled copy of pdf.js; the extracted **text layer** (and, when "include images" is on: for documents with a text layer, the detected **figures and tables cropped as images** — at most 4 per page and 20 per document, cropped on your device; for scanned PDFs with no text layer, **rendered images of whole pages**) is then treated **exactly like web-page content**: sent only to the AI endpoint you configured (or processed locally by Chrome built-in AI). Scanned PDFs with no text layer can only be summarized from page images — no OCR. Local `file://` PDFs require that you enable "Allow access to file URLs" for this extension in `chrome://extensions`; otherwise you can drop the file onto the reader page manually. History and translation cache are keyed by the original PDF's URL and title (same rules as section 3).

A PDF summary also carries a short "how much the model actually saw" statistic (text pages / scanned pages / figures detected and actually attached / whole-page images / why figures were left out / how many reading segments there were and how many were left unread; **numbers and reason codes only**, no page text or images), stored locally with that history record. Very long PDFs (more than about 60,000 characters of text, more than 8 figures, or more than 15 pages) are **read in segments** by default: each segment (≤28,000 characters, with the crops from its pages) is one model call and one final call merges them — at most 12 segments + 1; the "Read long PDFs in parts" setting turns it off, and Chrome built-in AI always makes a single call. What is sent is still the same document's text layer and crops, only split across several calls to your same endpoint — no new endpoint is involved. Detected tables are rebuilt as plain-text tables and sent with the text (no longer flattened into one line per cell).

**Chrome built-in AI mode**: if you choose "Chrome built-in AI" (Gemini Nano) in Settings, the **model inference for the content above runs entirely on your computer** and **page content is not sent to any external AI endpoint**. Note, however, that **fetching source images, reading YouTube captions, and the one-time download of the built-in model itself can still generate network requests** (to image CDNs, to YouTube, and to the browser's model-download service, respectively).

**Where results are shown, and what the web page can see**: the summary result, streaming output, and your follow-up input are carried, in side-panel mode, by an **extension-owned page** (extension origin); the on-page popup **by default** carries its content in an **extension-owned iframe**, so scripts on the page you're browsing **cannot read or alter** the results or your input inside it — and the iframe handshake requires a **one-time nonce** obtained through the extension's internal channel, which the host page cannot obtain or hijack. If the iframe is removed by the host page **or fails to load for any reason**, the default behavior is **fail closed**: the Extension closes the window and cancels the task — content is **never** handed back to the page automatically. In-page rendering happens **only if you have explicitly opted in beforehand** via the "Compatibility mode" consent setting; with that consent, a **benign load failure** (e.g. iframe load timeout) falls back to in-page rendering clearly labeled "**Compatibility mode**" — in that mode the content lives in the host page's DOM and is readable by page scripts, so use side-panel mode for sensitive content. In compatibility mode only the current result is placed in the page: related summaries are neither looked up nor shown (no other page's title, address or even a count is written into the host page). When an error card or the in-page mind map is written into the web page, URLs, account numbers, ARNs and key-shaped strings in the provider's raw error are masked as `***`; the Extension's own guidance text is left intact. Only the side panel shows the full original text (it is the Extension's own page); the pop-up result window's error card is drawn in the web page too, so it gets the masked version. See SECURITY.md for the full trust-boundary description.

### 3. Local history & cache of summaries / translations

For review convenience and token savings, results are kept in **your browser's local** `chrome.storage.local`:

- **Recent results (local history)**: summaries and selection results — each entry contains the **page title, the full original URL (query string included; kept local only, never sent out), a timestamp, the full summary/translation text, topic tags, and (when saved) follow-up Q&A** (from v1.51 also a **last-viewed time** `seenAt`: one timestamp updated when you open the same page again and the cache is hit, written at most once per day; local only, travels with backups, never sent — knowledge-base questions like "what did I read today" treat a record as in range when either its saved time or its last-viewed time falls in the period, so pages you re-read count too); for article pages where paragraph citations apply automatically, short excerpts of the cited source paragraphs are also kept so the viewer can show where each claim came from; for YouTube summaries, the citation time-range mapping (`citeTimes`) is also kept — stored locally only, used for jump-to-segment in the viewer; for full-page translation a **lightweight record** is also saved (page title, URL, and the number of translated paragraphs — the translated text itself lives only in the translation cache and on the original page, no full text is stored here), while selection translation saves the selected source text and its translation; disable "Keep a local Recent results history" to stop storing them. As of v1.20 this history is stored locally in an "index + per-record shard" layout, with the index itself split into fixed-size chunks (a purely internal storage-layout change; the older single-key index is kept after an upgrade only as a read-only copy for reading by an older version, and deleted records are filtered out of it in the background (at most about every 10 minutes, or the next time you use the Extension if its background had gone idle; if you downgrade within that window, the older version's list can still show a deleted record's title, but its content is gone and opens empty) — what is stored, its local-only nature, and your deletion/clearing controls are unchanged; the one-time migration backup **expires automatically after 7 days**, and **deleting an individual entry also removes it from that backup**, so "deleted means unrecoverable" is never undermined by the backup). "Recent results" has **no size setting** (it is limited only by your free disk space); beyond 50,000 records the oldest are removed automatically and the viewer page tells you how many; you can also see current usage and clean up old records in Settings. You can delete entries individually or clear everything in the viewer page. Topic tags are auto-generated by your configured AI endpoint by default (one extra tiny call after each summary; can be turned off in Settings; to reduce synonym tags, that call includes the names and confirmed aliases of your existing tags that literally overlap with the page) and are editable; tags also stay **local only** and power the Knowledge Graph page. Each entry can individually be excluded from the knowledge graph.
- **PDF reader citation excerpts and counts (v1.51)**: a PDF reader summary keeps at most 600 short excerpts (all of the first 120 paragraphs, then only figure/table paragraphs and paragraphs the summary actually cites, each at most 120 characters) plus each paragraph's page number — still local only, exported and imported with Recent results, deleted per record. It also records **counts** (text pages / scanned pages / figures detected and actually attached / whole-page images / why figures were left out / reading segments and unread segments), never any page text or image.
- **Tag relations (`kgRelations`)**: **this feature is suspended as of v1.16** (taken down for insufficient accuracy; the code flag `REL_FEATURE=false` hides its buttons and list in the UI; it will return after improvements). Existing data and handlers are retained but cannot be triggered. It was originally a **manually triggered** feature that sent tag text only (no page content) to your own endpoint; no such call happens today.
- **Topic pages (`topicPages`)**: "Generate / update" and "Generate / update mind map" on a topic page are features **you trigger manually** — they send the saved summaries under that tag to your own configured AI endpoint to synthesize one wiki page or one multi-level mind map; the result is stored **locally only** (the wiki is editable), and the whole topic page (including its mind map) can be deleted. "Clear recent results & translation cache" also deletes tag relations and topic pages.
- **Translation cache (per-paragraph keys `trc_*` plus a small index `trcLru` used for eviction; the older single key `translationCache` is merged in and removed after an update)**: translations of identical paragraphs (same model, same language), one entry per paragraph, so re-reading a page costs nothing; up to about 2,000 paragraphs / 2.5 MB, oldest-saved evicted first.
- **Tag concept table (`kbConceptStateV1` / `kbConcept_*` / `kbConceptEvent_*`)**: each tag's stable identity, its name and former names, aliases with their confirmed/rejected status, your rename/merge decisions, the public knowledge-base mappings (Wikidata Q-numbers) you picked or pasted, and the one-sentence definition the model produced for the concept. Local only; deleted by "Clear all local data"; the viewer's "Clear all" keeps only the parts still referenced by a topic page or decided by you.
- **Full-text index (`kbLex*` / `kbChunk_*`)**: term → record number and term frequency, plus paragraph boundaries — **no original text**, rebuildable at any time; after you delete a record, the terms cut from it are physically removed by a background sweep (about 15 seconds later while the Extension's background is running, otherwise the next time you use the Extension; sweeps are at least 10 minutes apart and deletions in between are folded into the next one); both "Clear knowledge-base data" and "Clear all" delete it.
- **Knowledge-base export / import (v1.21)**: under "Settings → Knowledge base → Backup & migration" you can export your knowledge base as a **JSON backup** (saved wherever you choose; when the total exceeds **40 MB** it is automatically split into **multiple volumes**, each a self-contained file that can be imported on its own and merged volume by volume). It contains: all recent-results records (including Q&A, tags, mind maps), topic pages, tag relations, the **tag concept table** (each tag concept's name and former names, the aliases you confirmed or rejected, the public knowledge-base IDs you pasted or picked, and your most recent rename/merge decisions — all your own data, local only; derived data such as the full-text index is not included and is rebuilt after import), a **randomly generated library identifier** (`libraryId`, used only to match up several backups of the same library; unrelated to your account or device; it stays inside the file), and a **non-sensitive settings subset** (custom prompts and display preferences) — it **never contains any API key** (the export uses a field allowlist, so credential fields structurally cannot enter the file). The whole operation is **pure local file I/O — nothing is sent to any model or anywhere else**. The export file contains your history summaries in plain text, so store it safely; on import you can choose "merge" (keep the newer version of each record) or "replace" (swap your whole knowledge base for the contents of the backup file). **"Replace" does not wipe first and write afterwards.** The imported records are written to a staging area and read back for verification first; only once everything is proven writable is the new index switched in by a **single atomic write**. Deleting the old data (records not present in the backup, topic pages, tag relations) happens strictly *after* that switch. So **if any step fails before the switch, everything is rolled back and your existing knowledge base is left untouched**; if the process is interrupted *after* the switch (for example by closing the browser), the new knowledge base is already usable and the remaining cleanup is completed automatically from a recovery journal on the next start. One thing to be clear about: once "replace" succeeds, records that are not in the backup file are deleted by design — that is what "replace" means, not a failure.

**Non-persistent session context (`chrome.storage.session`)**: so that you can keep asking follow-ups after the Service Worker is recycled, the side panel can restore its view when reopened, and a few bookkeeping records survive a Service Worker restart, the Extension keeps **thirteen** keys in `chrome.storage.session` (a prefixed family such as `conv_*` counts as one). For every key we state **what it holds, whether it contains a URL, when it disappears on its own, and whether "clear everything" removes it**:

- **Follow-up conversation context (`conv_*`)**: the current tab's follow-up context — **the full extracted text of that page (up to 512 KB; only longer pages are truncated), the full summary, and every previous Q&A turn**, plus a snapshot of the model settings and **one random document code** (`docNonce`, as of v1.49; not a URL, no page content, never sent anywhere — it only lets the Extension still tell "has this tab moved to a different document?" after the Service Worker has been recycled, so that pressing Back clears the previous page's context). **As of v1.23 this snapshot always has every API-key field stripped out** (older snapshots written by earlier versions are sanitized in place on load) — **the follow-up context snapshot never contains a key**; follow-up calls re-resolve credentials from your current live settings instead. (Note: if you opt into the "keep keys only until the browser closes" mode described above, your keys are stored in a separate item, `sessionCreds`, in this same storage area — that is a storage location you chose deliberately, and is distinct from this conversation snapshot.) No URL. Removed on a real navigation (you move to a different page) or when you close the tab — **reloading the same URL does not clear it** (the page is loaded again, but the address has not changed, so the context stays), and **a same-document History API change does not count** (an infinite-scroll site rolling into the next article, a single-page app switching routes: the address changes but the document is the same one, so the context stays until a real navigation); "clear everything" and the viewer's "Clear all" both **actively remove it and verify by reading back**. For medical, intranet, or otherwise sensitive pages, be aware that **the full text of the page you just summarized stays here until a real navigation (you move to a different page), the tab is closed, or you clear** — the kind of "page change" where only the address bar changes and the page is not reloaded does not remove it.
- **Side-panel replay log (`panel_*`)**: the already-rendered result messages in side-panel display mode, so the panel can replay after a reopen / SW restart; it also holds one view-state entry for that result (which round of suggested questions you dismissed with ✕, and whether related summaries are collapsed), so a replay or a revised summary does not bring back what you closed. No URL. Removed on a real navigation (you move to a different page) or when you close the tab (reloading the same URL does not clear it, and a same-document History API change does not count, as with `conv_*`); "clear everything" **actively removes it and verifies by reading back**.
- **API keys in "keep keys only until the browser closes" mode (`sessionCreds`)**: present **only** if you chose that mode under Settings → Key Storage (see "Where your API keys live is your choice" above); never written to disk, never synced, cleared automatically when the browser closes, and removed when you switch storage mode or press "Clear keys". No URL. This is a separate item from the conversation snapshot above. **"Clear everything" deliberately leaves it alone** — it is the key location you chose, and clearing data is not the same as signing out.
- **Running-task snapshot (`bgActiveTasks`)**: which kinds of task are running in which tab and when each one started — **task kind plus a timestamp only; no page content and no URL**. It exists so the toolbar popup can show queue state without waking the Service Worker, and so running tasks survive an unexpected Service Worker restart. It is maintained by the task lifecycle itself: with no task running it is an **empty snapshot** (the key is removed only after the Service Worker's cold-start reconciliation); "clear everything" does not delete it separately — clearing first aborts every running task, so the snapshot becomes empty as a result.
- **Translation round bookkeeping (`trrun_*`)**: per-tab state that lets a "fill in the gaps" round know what the previous round already delivered. It holds **content hashes, counters, short flags, and the URL of the page being translated** — and **zero characters of the page text, zero characters of the translation** (the value that does hold translated text is deliberately not mirrored here). The URL is used only so the next round can confirm it is still looking at the same page; it is never sent anywhere. Removed on a real navigation (you move to a different page) or when the tab closes (reloading the same URL does not clear it, and a same-document History API change does not count, as with `conv_*`); it also carries a data epoch, so clearing the translation cache makes any leftover entry expire immediately; **as of v1.46 "clear everything" actively removes it and verifies by reading back**.
- **Last translation outcome (`bgLastRunOutcome`)**: one record per tab, at most 20, describing how the most recent full-page translation ended — outcome kind, paragraph counts, per-class integer counters (`diag`, integers only — from v1.51 including the paragraph and call counts of the residue / date / proofread checks and the collection duration in milliseconds with send / arrival timestamps — no page text), a flag recording whether the page was replaced while the translation was still running plus its timestamp (`docLost`／`docLostAt`, a boolean and a number), a run id, the status/error card text, and, so that a late result can be re-delivered to the right page and never to a different one, **the URL of the page that was being translated**. That URL is kept **solely** for this identity check and is never sent anywhere. **It is not removed when you navigate away or close the tab** (that is precisely why it exists — after the page changes it still has to know whether to re-deliver); it is only overwritten by the same tab's next translation, or trimmed when there are more than 20 entries; **as of v1.46 "clear everything" actively removes it and verifies by reading back** (before v1.46 it did not, and the record stayed until the browser closed).
- **Unsaved topic-page draft (`topicDraft_*`)**: while you are editing a topic page's wiki text, the in-progress draft is kept per tag so that an accidental reload or a Service Worker restart does not lose what you typed. It holds **the draft text you wrote** plus two markers — the clear generation and a version code of the page's saved text (its length and a hash, used to notice that another tab saved first) — nothing else, and no URL. It is removed as soon as the draft is saved or discarded; it **deliberately survives reloads and navigation** (that is its purpose); **as of v1.46 "clear everything" removes it together with the topic page itself and verifies by reading back**, so no orphaned draft is left behind; "clear knowledge-base data" removes it too. A topic page that is still open **in edit mode** at the moment you clear is shown a notice right away ("The knowledge base was just cleared or imported elsewhere; this edit will not be saved automatically — press Save to save the current content.") and stops writing the draft back automatically (the text stays on your screen; pressing "Save" stores it as new content).
- **Learned output-limit table (`bedrockClampV1`)**: for the Bedrock provider, a table of "model ID → the output-token limit that model actually accepts", so that after a Service Worker restart the same model does not hit the same limit error and waste a request. **Model identifier strings and numbers only — no page content, no URL, no key.** Gone when the browser session ends; "clear everything" does not delete it (it is not your data, it is a performance self-learning table).
- **Learned output-limit table (`openaiClampV1`)**: same as above, for OpenAI-compatible endpoints. Same contents, lifetime, and clearing behaviour as `bedrockClampV1`.
- **Diagnostics ring (`bgTaskLedgerV1`)**: snapshots taken **when a task ends**, for the last 50 tasks, so that "Export diagnostics" can hand us something useful when you report a problem: task id, kind, how it ended (including a cancellation reason code), a few timestamps (start / extraction done / collection start and end / first byte / the moment the page was replaced mid-task / end), how long it queued and whether it was admitted to start, the cache decision, whether the record was written back, the local record id and document id of the result (internal identifiers, not URLs), provider and model name, the endpoint's **masked label** (host plus a 4-character hash only), error code (for example the category of a failed injection into, or extraction from, the page), integer counters, and the model-call ledger (number of calls, HTTP attempts, token totals); for YouTube video pages, three fixed-vocabulary fields are also kept: the caption source kind (captions / video description / comments / none), which of two internal fetch paths was used, and a reason code when captions could not be obtained (e.g. rate-limited, no caption track) — never the video ID, URL or caption text; tasks on the PDF reader page also carry **layout counts** (numbers of paragraphs, formulas, tables and figures, and how many pages got the second layout pass — integers only; no PDF text, URL or title) — for a public paper, this combination of counts may be enough to guess which document it was (for example 22 pages, 5 tables, 12 figures), so leave the file out if that matters to you; summary tasks also carry a **processing trace**: how many paragraphs and images were extracted, the names and lengths of the instruction clauses sent, and the reason for each automatic correction and whether it was adopted — fixed codes and numbers only, plus one yes/no flag in the extraction figures (whether only title-level metadata could be read). **No URL, no page text, no key** — the writer only stores allow-listed fields and drops any string that looks like a URL. Gone when the browser session ends; **both "clear everything" and the viewer's "Clear all" actively remove it and verify by reading back**.
- **Diagnostics "include content" flag (`diagVerboseV1`)**: exists only while you have ticked **"include content"** next to "Export diagnostics" in Settings; it means "for the tasks that follow, also keep the model's raw output". Cleared automatically after you export (the checkbox in Settings follows), removed by "clear everything" and the viewer's "Clear all", and gone when the browser closes.
- **Diagnostics detail (`bgDiagVerbose_*`)**: produced only while the flag above is on, for tasks started afterwards: on the summary side the model's **raw output text** (at most 64 KB per call); on the translation side, per-segment source snippets, raw model replies, cleaned translations, verdicts and cache decisions. **This is the only diagnostic data that contains page text and model replies** — it exists only after you explicitly tick the box, is written to a file only when you press "Export diagnostics", and is removed right after the export; if you never tick the box, not a single character of it is ever stored. "Clear everything" and the viewer's "Clear all" remove it too.
- **Wipe generation (`wipeGenV1`)**: **two integers** (how many times data has been cleared, and when) — incremented by every "clear everything", "clear knowledge-base data", or backup import. It lets a topic-page editor that is still open at the moment you clear learn that "the data was cleared elsewhere", so it stops writing your in-progress edit back automatically (the text stays on your screen; pressing "Save" stores it as new content). No content, no URL; gone when the browser session ends; "clear everything" does not delete it — it records the very fact that a clear happened.

Every key in `chrome.storage.session` is **never synced, never written to disk, and never sent to the developer**, and **all of them are gone at the latest when the browser session ends**. "A real navigation or closing the tab clears it" is true only for `conv_*`, `panel_*`, and `trrun_*` (a real navigation means you move to a different page; reloading the same URL does not count — the document is replaced, but those three keys are deliberately kept so that a reload does not kill the tab's running tasks; a same-document History API change — infinite scroll, a single-page app switching routes — does not count either, and these three keys stay until a real navigation); `bgLastRunOutcome` and `topicDraft_*` stay by design until the next overwrite, a save/discard, or "clear everything"; the three diagnostics keys `bgTaskLedgerV1` / `diagVerboseV1` / `bgDiagVerbose_*` stay until "clear everything" or a diagnostics export (the latter two are cleared right after export); `sessionCreds`, `bgActiveTasks`, the two learned tables, and `wipeGenV1` follow their own lifecycles as described above.

**Your controls:**

- Settings → "Keep a local Recent results history" can **turn history off** (recommended for sensitive content such as intranet, medical, or financial pages).
- Settings → "Reuse recent results for repeated content" controls the **translation cache**.
- Settings → "Knowledge" → "Clean up old records" deletes, in one go, every record **saved more than 30 / 90 / 180 / 365 days ago** (the confirmation says how many and up to which date; all record types, and they are removed from the knowledge base too); the same section shows current usage (MB and record count). "Recent results" has **no size setting** — beyond 50,000 records the oldest are removed automatically, and the viewer tells you how many.
- The "Recent results" viewer page lets you **delete entries individually** or **clear everything** (you can export a backup first); as of v1.23 the viewer's "Clear all" also **actively removes the follow-up conversation context (`conv_*`)** rather than passively waiting for the session to end.
- Settings → "Clear recent results & translation cache" deletes **history, cache, knowledge base (tag relations, topic pages), conversation context, side-panel replay logs, translation round bookkeeping, the last translation outcome, and unsaved topic-page drafts** with **one click** (each category is verified by reading back; if anything is left behind the operation honestly reports failure); removing the Extension also deletes all local data. The only `storage.session` items "clear everything" deliberately leaves alone are your opted-in `sessionCreds`, the task snapshot `bgActiveTasks`, and the two learned output-limit tables (see the per-key list above); like everything else they are gone at the latest when the browser session ends.
- **Clearing is complete (v1.21, scoped)**: before any clear operation runs, the Extension **first aborts the in-flight tasks that correspond to what you are clearing** — "clear history / clear everything" aborts summaries and translations in every tab plus long-running knowledge-base tasks; "clear translation cache only" aborts only translation tasks (a paid summary running in another tab is unaffected); "clear knowledge-base data only" aborts only the long-running knowledge-base task — and advances the matching internal **data-generation gate**: a task still finishing at the moment you clear **will not write its data back**, so cleared data never "comes back to life" — this also covers Wikidata auto-mapping results still in flight when you clear, and the topic pages and tag relations of a backup that was being imported at that moment (`SEC-1520-7` / `-14`).

On both of this version's AI paths, all of this stays **on your device only** — never sent to a developer-operated server or intermediary. Exactly three things send any of it to the AI endpoint you chose (or to on-device Chrome built-in AI): **auto-tags**, which run **automatically** after each summary (the summary excerpt, up to ~4,000 characters; can be turned off in Settings); the standalone **suggested-questions** call, which also runs **automatically** and sends the same summary excerpt (up to ~4,000 characters) on selection summaries, when the question section of a full-page summary fails to parse, on Chrome built-in AI's two-stage flow, and when a cache hit finds a record that has no questions yet (can be turned off in Settings; when a full-page summary goes to your own AI endpoint, the questions are produced inside the same single summary call and nothing extra is sent); and the content sent when you actively use topic pages / mind maps / knowledge Q&A. There is one further optional path that **does not go to an AI endpoint and is off by default** (next section): once you turn on "Allow public knowledge-base lookup (Wikidata)", only one concept name goes to Wikidata when you click "Find public mapping", and only the new tag names of each summary (at most 6) go to Wikidata when its tags are generated (untick "Automatically look up public mappings for new tags" to stop the latter).

**Proofread once more after translating** (v1.51; a sub-option of "AI refined translation", on by default): with it on, some paragraphs (those carrying causal, negation or numeric content — and, when the source is written in a less common script such as Sinhala, every long paragraph) have their source text and draft translation sent once more to the same model (or your primary model) for proofreading — apart from the date described next, nothing new is sent, the same paragraph simply goes out a second time; paragraphs whose translation still carries source-language words, or whose dates are ambiguous, are likewise re-sent at most once each. The call caps and billing are in the translation row of DATA_FLOW.md.

**Today's date when a paragraph mentions a year** (`TRC-1520-11`): when a paragraph mentions a year (a Gregorian year in any numeral system, or a Buddhist, Japanese-era or Minguo year), the translation and proofreading instructions also include today's date from your device (the date only — no time or time zone) so the model can tell past events from forecasts; paragraphs that mention no year get nothing extra.

## Optional public knowledge-base lookup (Wikidata)

The concept editor on a topic page lets you attach a public knowledge-base mapping (a Wikidata Q-number) to a tag concept. You can **paste** a Q-number yourself (zero network traffic), or turn on an option that is **off by default** to look up candidates (the setup wizard's last step, "Allow public knowledge-base lookups (Wikidata) to match concepts across languages", and Settings → "Knowledge" are the same switch; both start unticked):

- **Off by default**: while Settings → "Knowledge" → "Allow public knowledge-base lookup (Wikidata)" is unchecked, the Extension **makes no connection to www.wikidata.org at all**; clicking "Find public mapping" only shows a notice.
- **What is sent**: once enabled, when you click "Find public mapping" on a topic page, one GET to `https://www.wikidata.org/w/api.php` carrying **that concept's name — one string** (in your interface language); while the sub-option "Automatically look up public mappings for new tags" is ticked (**ticked by default**; effective only while the option above is on), the same endpoint also receives **each new tag name of a summary** (at most 6 per summary, one request per name; language = the tag's language; for ambiguous names at most one extra `wbgetentities` call for type and sitelink count) while that summary's tags are generated. Names already looked up are not re-sent for 30 days (7 days for misses); results and the "already looked up" record stay on this device (`kbWdCacheV1`, removed by Clear data). The manual button never reads this cache and contacts Wikidata every time you click. The name is read from the concept table by the background script; it is never the content of any input box on the page. Every request carries a self-identifying header, `Api-User-Agent: WholeTake/<extension version> (<project URL>)` — Wikimedia asks automated clients to identify themselves; it says which version of the extension sent the request and nothing about you (if your network strips that header, the same lookup is retried once without it). As with any network request, Wikidata's servers also see your IP address and the ordinary headers your browser sends.
- **What is not sent**: no article text, no summaries, no other tags, no URLs, no cookies; the topic-page lookup is never automatic (with the main switch on but the sub-option below unticked, the extension looks things up only when you click).
- **Automatically look up public mappings for new tags** (a sub-option shown under the switch above, **ticked by default** but **effective only while that switch is on** — the main switch is off by default, so the default is still zero network traffic; once you turn the main switch on, automatic mapping comes with it unless you untick this sub-option. When upgrading: if your main switch was already on, the sub-option keeps whatever you had chosen and the upgrade does not start automatic lookups; if your main switch was off, the sub-option becomes ticked — it has no effect while the main switch is off, so the upgrade itself causes no connection, but automatic mapping will start whenever you later turn the main switch on): after a summary produces topic tags, each **new** tag of that summary is looked up once with the same query (**the tag name — one string**, at most 6 lookups per summary, at most one extra type/sitelink query for ambiguous names; never the title or content); names already looked up are not re-sent for 30 days (7 days for misses), and the results plus the "already looked up" record stay on this device (`kbWdCacheV1`, removed by Clear data, never exported). A mapping is attached automatically only for a candidate whose **label matches exactly in a matching language** (several exact matches are narrowed by type / language / description / sitelink count, and nothing is attached if they still tie; without an exact label match only a single alias match is accepted), marked "Auto-mapped, pending" — on the topic page you can ✓ confirm or × reject it; mappings you already confirmed or rejected are never overwritten by an automatic result, and a rejected one is never revived by a later automatic lookup; otherwise nothing is stored; nothing is looked up while offline. This runs in the background, but only right after a summary you triggered — it never wakes up on its own; the manual "Find public mapping" button still contacts Wikidata only when pressed and does not read this cache.
- **What is stored**: the response is at most 8 candidates (Q-number, label, one-line description); a manual lookup stores **only the one you pick** (as "proposed" first; you can confirm or reject it), an automatic lookup stores only the single "pending" mapping it attached (plus the decided QID / label / description in `kbWdCacheV1` — never the candidate list); both live inside the local tag concept table and are cleared together with it. An automatic mapping also records the label Wikidata returned in your language as a "Wikidata proposed" alias (removable, not used for tag resolution); once you ✓ confirm a mapping, later foreign-language tags carrying the same Q-number are merged into that concept. Q-numbers produced by a model from memory are never accepted.
- **Failure never affects local features**: offline, timeout or an error from Wikidata only shows a notice; everything local keeps working.
- Like other settings both switches sync with Chrome (they take effect on every device signed in to the same account), but they are **never written into a knowledge-base backup file** — importing a backup from another machine will not turn them on for you. For Wikidata's handling of the request see the [Wikimedia Foundation Privacy Policy](https://foundation.wikimedia.org/wiki/Policy:Privacy_policy).

The Extension sends the page content described above to the AI endpoint you specify. You are responsible for understanding and agreeing to that endpoint's privacy policy. Common endpoints:

- **Chrome built-in AI (Gemini Nano)**: **not a third-party cloud service** — key-free, model inference runs entirely on your device, and summarizing/translating **generates no external request for inference** (only the one-time download of the model itself is performed by the browser from Google's model-download service; your content is never part of it)

- **Official OpenAI API**: see the [OpenAI Privacy Policy](https://openai.com/privacy)

- **Wikidata (optional, off by default)**: once turned on, receives one concept name when you click "Find public mapping" by hand, and each summary's new tag names (at most 6) when its tags are generated (the sub-option "Automatically look up public mappings for new tags" is ticked by default and can be unticked) — see the section above; see the [Wikimedia Foundation Privacy Policy](https://foundation.wikimedia.org/wiki/Policy:Privacy_policy)

The developer is not responsible for any third-party service's data handling.

## Permissions

The Extension requests the following Chrome permissions, each used only for its core features:

| Permission | Purpose |
|---|---|
| `storage` | Stores the settings above, plus "Recent results" and the translation cache (local `chrome.storage.local`, never synced; "Recent results" has no size setting and is limited only by your free disk space — beyond 50,000 records the oldest are removed automatically and the viewer tells you so; delete entries or clear everything in the viewer, or clean up old records in Settings — see section 3 above) |
| `scripting` | Injects the content script into the page to show results and translations |
| `contextMenus` | Adds the right-click "Summarize / Translate selection" items (shown when text is selected) and "Summarize / Translate link in new tab" (shown on http/https links: opens a new tab for that link and runs on that page once it has loaded); runs only when you click a menu item |
| `sidePanel` | Display mode (default since v1.28): summary results are shown in the browser side panel, **only on tabs where you triggered a summary** (per-tab content; the panel does not follow you to other tabs); you can switch back to the in-page dialog in Settings. The panel only renders results you explicitly requested; it reads nothing by itself |
| `unlimitedStorage` | Keeps the local "Recent results" history and knowledge base from being capped by the browser's default local-storage quota (the Extension itself has no size setting — only a 50,000-record safety limit). The data still lives **only on your device** — never synced or uploaded |
| `host_permissions: <all_urls>` | Lets the Extension work on any site you're reading, and lets the service worker fetch your configured AI endpoint and page-image CDNs (CORS bypass); since v1.49 it also lets the Extension download again the PDF you are viewing from its source (the Extension's background downloads it once and hands it to the reader — see "PDF summaries / translations" above); and it lets the Extension inject its content script into the new tab opened by "Summarize / Translate link in new tab" (that page is not the tab you were on when you clicked the menu) |
| `declarativeNetRequestWithHostAccess` | Used ONLY to strip the `Origin` header from requests the Extension itself sends to your own configured local AI endpoint (loopback such as Ollama / LM Studio). Local servers reject the browser-added `Origin: chrome-extension://<id>` with a CORS 403; removing it lets your own local model accept the request. The rule is scoped by `initiatorDomains` to THIS extension's initiator only (never any web page), covers loopback automatically and LAN only after you explicitly opt in, and NEVER public endpoints — one `modifyHeaders(remove Origin)` rule per configured local endpoint origin (typically one, at most four - deduplicated across the main/summarize/translate/knowledge endpoints), and nothing else: it does not block, redirect, read ordinary web-page traffic, or read/modify cookies |

The content script is injected **on demand** (since v1.37; zero resident scripts since v1.39): **no code from this extension is resident on any web page** — the manifest declares no `content_scripts`. The full script loads into the current tab only when you trigger a summary/translation (keyboard shortcut, context menu, or popup) — or, for a right-clicked link, into the new tab it opens; if the page swaps documents while that action is still running (for example you reload it), the same script is injected into the same tab once more so the action can finish or the side panel can re-attach to the page (no new task is started); and the first time compatibility mode shows a result inside the page, the Extension's own bundled formatting library is injected into that same page. Content is extracted only when you explicitly trigger it, never read or uploaded in the background.
